## What was changed this session

### host/config.py
- Added `GATE_DROPOFF_DEG = 45` — separate gate angle for dropoff. At the hole the gate only opens 45° (enough for balls to roll out, narrow enough not to jam the wall). Pickup still uses `GATE_OPEN_DEG = 90`.
- Added `HEADING_LOOKAHEAD_PX = 100.0` — distance at which the nav loop starts pre-aligning heading toward the next waypoint.

### host/nav.py
**Fixed a latent bug:** `in_close_approach` and `step_mm` were computed after the heading block that referenced them — would have crashed on first real run.

**Heading lookahead (the "during approach" fix):**

When the robot is between 40 px and 100 px from a waypoint, `heading_target` blends linearly from the current waypoint's bearing toward the next waypoint's bearing:

- At 100 px out: `heading_target = bearing_to_current` (no change)
- At 40 px out (close-approach boundary): `heading_target = bearing_to_next` (fully pre-aligned)

The blend uses a separate variable from `move_err` (which is still computed purely toward the current waypoint). This matters because:
- `err` (from `heading_target`) drives TURN decisions — robot pre-turns during approach
- `move_err` (from `bearing`) drives REVERSE decisions — robot doesn't spuriously reverse just because it's facing the next waypoint

Guard: lookahead only activates when the next waypoint's bearing is within 90° of the current — prevents corner-cutting around obstacles.

Result: by the time the robot arrives at a waypoint, it's already facing roughly the right direction. Post-arrival heading correction becomes small or zero.

### host/loop.py
- Dropoff gate now sends `GATE_OPEN:45` (via `GATE_DROPOFF_DEG`) instead of `GATE_OPEN:90`.
